# Erasing an attendee's personal data

`eraseAttendees` ([`packages/tickets/src/erase-attendees.ts`](../../packages/tickets/src/erase-attendees.ts)) anonymises attendees in place. The row stays, so the Reports totals and the admission log keep their numbers; capacity is the one thing that moves, because a person not admitted yet on an event that is not archived becomes `cancelled` and their place is free again. Nothing that identifies the person or opens their ticket is left. It is a different action from removing an attendee (hard delete, for mistakes), which changes Reports.

## What happens

Run inside the caller's transaction, once per attendee that is not erased yet.

| Where | What erasure does |
|---|---|
| Attendee | Name and email become placeholders (`Erased attendee`, `erased-<id>@erased.invalid`). Names, company, department, custom answers, ticket token, QR payload, agency ids and public ref are cleared. `erased_at` is set. Admission time is cut to the hour in the event timezone. |
| Attendee status | A person not admitted yet, on an event that is not archived, becomes `cancelled`, so their place is free. Otherwise the status stays. |
| Notes, activity log | Deleted. |
| Check-ins | Kept without notes, time cut to the hour. Because of that cut, "undo the last scan on this device" refuses when an erased scan on the device could have been the last one (it cannot tell), instead of undoing an older, live attendee. |
| Email deliveries | Kept as rows for the Mail report, without recipient, subject, body, provider message id and error text. Mail still waiting to go out is cancelled first. |
| Wallet pass | Links, device and tokens cleared. Provider ids stay until the pass is deleted at the provider. |
| Central audit log | The "created manually" entry loses the name and email it recorded. |

## The API

`POST /api/admin/events/:eventId/attendees/:id/erase` and `POST …/attendees/bulk-erase` (Administrator and Superadmin of the event; allowed on an archived event). In one transaction they run `eraseAttendees`, blank the erased addresses in the saved results of the event's imports (`scrubImportJobResults`) and write the audit entries (the event's activity log and the central audit log, **ids and counts only**, `method: "erase"`). After the commit they delete each erased attendee's wallet pass at the provider (`deleteErasedWalletPasses`, from the event's credentials alone, whatever the Wallet switch says) and mark it removed.

The answer is `{ erased, already_erased, not_found, wallet_pending, wallet_removed_ids }`. `wallet_pending` counts erased attendees whose pass is still to be deleted at the provider (it failed, the event has no credentials, or the 90 s budget of one request ran out). `wallet_removed_ids` lists the attendees whose pass was still to be deleted when the follow-up started and no longer is (deleted by this request, or by one running at the same moment), read from the database before and after the follow-up; a pass that never reached the provider (no provider id), or was removed before, is not in it, so a screen can say "deleted" only for a pass that was. Both endpoints spend the attendee-mutation budget of the user and event (20 a minute). When the event has wallet credentials, the single one also spends the wallet-action budget it shares with the other single-attendee wallet actions (10 a minute), and the bulk one the wallet-action-bulk budget (10 in 10 minutes), as bulk delete does. One follow-up runs per user and event at a time. A provider that answers 404 counts as "deleted", so a pass issued under an API key or account that was changed later is marked removed while it may still exist. **Repeating the request is the retry:** attendees already erased change nothing in the database, only their pending passes are tried again. Nothing else in the product deletes an erased attendee's pass.

The database enforces the result: `Attendee_erased_carries_no_personal_data` rejects any row with `erased_at` set that still holds a name, email, credential or answer, and a trigger refuses to change or clear `erased_at` once it is set (a delete of the row is still allowed).

## The screens

Where an Administrator or Superadmin reaches the erasure (`apps/admin`):

| Screen | What it does |
|---|---|
| Attendees list, bulk bar, **More actions** | **Erase personal data** for the selection (`BulkEraseDialog`, `bulkEraseAttendees`). No typed name. The dialog says how many of the selected people are not checked in yet, so that their places become free (`placesFreedBy`, `freedPlacesLine`; the same rule as the one-person dialog, and never on an archived event). When the server confirms, the list at once redacts those rows in place (`redactedRowsAfterErasure`: personal data out, the check-in time cut to the hour of the event's zone like the server does, `truncatedToEventHour`, the status the server sets, mail that was queued cancelled, and the pass marked as removed at the provider for the people the answer lists in `wallet_removed_ids`) and then reads the server's version, so nothing of the people stays on screen while that read waits; if the read finds its page empty (the erasure took the last rows of the last page), the list steps back to the last page that exists instead of saying "No matches". |
| Attendee page, **More actions** | **Erase personal data** for one person (`EraseAttendeeDialog`, `eraseAttendee`). The attendee's name has to be typed. When the server confirms, the page at once swaps its local copy for a redacted one (`redactedAfterErasure`: personal data out, the check-in time cut to the hour of the event's zone, the status the server sets, mail that was waiting to go out cancelled, and the pass as the answer left it: still at the provider when `wallet_pending` says so, which keeps the Try again there, and deleted now only when `wallet_removed_ids` lists the person) and then reads the server's version, so nothing of the person stays on screen while that read waits or if it fails. The page never turns an erased attendee back into one that is not (`isOlderThanErasure`, checked in `applyDetail`, the one place every answer goes through), so a read or a change (a note, say) that was already on its way cannot bring the person back when its answer arrives late; and a read that answers after a newer one is dropped (`loadSeqRef`), so an older answer cannot put back what the newer one changed (a pass deleted by Try again, say). The line "Not checked in yet, so their place becomes free" shows only when the erasure will cancel the attendee (`erasureFreesPlace`, the same rule as the function). |
| Attendees list, line under the table | Erased entries are left out (`include_erased` is not sent). The line says how many (`erased_count`, event-wide, however the list is filtered) and **Show erased** lists them (the line then says they are included, without a number, because the rows are filtered and paged): muted rows, "Erased attendee" with a dashed **Erased** mark and "Erased on <date>" in place of the name and address (the placeholders the server sends are never shown), and a checkbox that stays off. **Select all** skips them. |
| Attendee page of an erased attendee | `ErasedAttendeeView`: read-only, every field that held personal data reads **Erased**, the check-in time reads "Around HH:MM". The Wallet card says what became of the pass: deleted on a date, or still to be deleted (`wallet_pass_delete_pending` in the detail response, true only for an erased attendee whose pass has a provider id and no `provider_removed_at`) with a **Try again** button. |
| **Personal data erased** dialog | Shown after an erasure when `wallet_pending` is above zero (`useEraseWalletResult`). **Try again** sends the same request again, which for people who are already erased only retries the wallet delete. It is a Retry of a dialog: the failure of the earlier try stays on screen, with the busy button, until the answer is in; the button stays busy for 400ms at least; and a failure that repeats is announced again. What the answer says about the pass is applied to the attendee page at once (`withWalletOutcome`) before the page reads the server's version, so a read that fails cannot make a deletion that worked look lost. |

Erase is not behind the archived-event guard, like the API.

## Rules for code

- **New column or table on an attendee?** `packages/tickets/test/erasure-inventory.test.ts` fails until you decide what erasure does with it (cleared, kept, deleted). Add the behaviour to `eraseAttendees` and its test too.
- **Never reuse an erased row.** `erased_at` is the marker; `status` is not (it drives capacity and issuing). Code that sends, issues, edits or checks in an attendee must refuse an erased one. Ticket issuing and the event-day operations (check-in, undo and revoke, item hand-outs, notes, the activity log, the door search and card) already do.
- **Writing a row that belongs to an attendee?** Call `lockAttendeeRow` ([`attendee-lock.ts`](../../packages/tickets/src/attendee-lock.ts)) first in the same transaction. A check-in, note, item state, log entry, wallet pass or email delivery is inserted under the weakest row lock, so without it the insert can wait for a running erasure and land after it. A filter such as `attendee: { erased_at: null }` does not close that race. A write that updates the attendee row itself puts `erased_at: null` in its own `where` instead. A transaction that deletes an attendee and its children calls `lockAttendeesForUpdate` first, so it takes the attendee row before the children like everything else (the other order can deadlock).
- **Only reading?** No lock. A plain read (the door search, the recent scans) is one statement, so it does not wait for an erasure that is still open: it sees the attendee as it was before that commit, or the placeholder after it. Both are fine, because what the operator was handed a moment before the commit cannot be taken back by any lock. Filter `erased_at: null` and leave it there. Take the row lock only when a read is followed by a write, as the card is (it inserts the pending item states).
- **Never log or audit names or emails** of the people erased. Ids and counts only.
- **The admin API marks and refuses.** `erased_at` is in the attendee list rows and the detail DTO; the list hides erased attendees unless `include_erased=1` and returns `erased_count` (event-wide) for the "N hidden" note. Every single-attendee action answers `409 { error: "attendee_erased" }`, bulk actions skip erased attendees, and exports and the personal data export leave them out. Delete (Remove) is the one action that keeps working on an erased attendee. An erasure that commits after the route's plain read is told apart too: the domain functions that lock the attendee (revoking a check-in or an item, editing or deleting a note) mark the error they throw with `erased`, and the route answers `attendee_erased` (`attendeeErasedAnswer`) instead of the words of that error or a 404 for a note the erasure deleted. Counts that are acted on (the bounced count, the revoke counts, the installed-pass counts of the Danger Zone) and the activity feeds leave erased attendees out; the Overview tiles keep counting them, like Reports and capacity do, so a tile and its total stay consistent.
- **The last check before something leaves.** The context a route loads and the rows an export reads come from plain queries, which do not wait for an erasure that is still open. So the last step before a wallet pass is changed at the provider (void, also in bulk and for the whole event, restore, push the content, delete, the bulk delete, and the void or restore that follows a status change or a bulk pass revoke), before a pass is read there for a status refresh (single, bulk and event-wide), and before an export file is built reads the attendee under their row lock, in a short transaction of its own (`attendeeIsLive`, `requireAttendeeStillLive`, `refreshWalletPassStatusUnlessErased`, `keepLiveRows`). An erasure that is still open is waited for: a wallet action then answers `attendee_erased` (a bulk action counts the attendee as skipped) and an export leaves the attendee out. The lock ends with that transaction, before the provider call or the build of the file, so an erasure that commits in the gap does not stop a call or a file that is already under way: the provider voids, restores, updates or deletes a pass that the erasure is about to delete anyway, and the file holds the person as they were when it started. What follows is detected, not undone: the write back onto the pass row takes the attendee's row lock again and leaves the row as the erasure kept it (`updateWalletPassUnlessRemoved` answers `attendee_erased` or `wallet_pass_removed`, not one `null`), and Delete does not touch the pass row an erasure keeps. A ticket link that an admin copies, and the preview of a sent message that puts the same link into the stored text, check the attendee before the link is put together and log the retrieval under the lock (`logTicketLinkRetrieved`, which uses that `writeActionLog` returns false for an erased attendee): an erasure that commits in between answers `attendee_erased` (the preview answers the empty message it gives once the erasure is done) and no link is handed out. The status refresh is the exception to that write back: it records registration counts, the first download and the lifecycle the provider reports, which are retained facts about the pass and not personal data, and the periodic sync and the webhook write the same columns without any attendee lock, so only its read is guarded.
- **`@erased.invalid` is reserved.** Import, manual add and edit reject such an address, and a second CHECK refuses it on a live row: a live attendee holding `erased-<id>@erased.invalid` would make the erasure of `<id>` fail on the unique (event, email) index. The migration moves any address already in that namespace to `<local part>+<attendee id>@legacy.erased.invalid` before the constraint is added, so the upgrade cannot fail on old data.

## Not done by the function

- The pass at the provider is not deleted (network call). The function returns `walletTargets`; the caller deletes them after commit and stamps `provider_removed_at`. Until then the row keeps its provider ids so the delete can be retried, and a pass with provider ids and no `provider_removed_at` on an erased attendee means "still to delete at the provider". The caller should re-read the attendee's wallet pass after the commit rather than trust `walletTargets` alone. A pass created by a request that started before the erasure ends up as exactly such a row: its install links are not saved, and the request deletes it at the provider right away (or leaves the row for the retry if that fails). The retry is the erase API repeating its provider deletes: calling it once more for the same attendees tries every pending pass of theirs. Nothing retries on its own yet, and a failed delete is logged as `wallet_pass_erased_delete_failed` (System logs), so a worker sweep of pending passes of erased attendees is the follow-up to consider.
- Event-level copies still left: files written by earlier exports (CSV, XLSX, PDF) and the staged CSV of a failed import stay in storage; wallet message job requests keep the pseudonymous attendee ids. Saved import results are blanked by the API (above; an import that is still running when the erasure commits writes its list afterwards and is not covered). An entry counts as mentioning the address when it holds it as a whole (`containsAddress` in `erase-job-results.ts`): a full stop at the end of a sentence, brackets, double quotes and quote marks (`'a@x.com'`) around it do not hide it, while a longer address that merely ends or starts with it (`banana@x.com`, `_a@x.com`, `=a@x.com`, `o'brien@x.com` for `brien@x.com`, `a@x.com.au` for `a@x.com`) is another address and is left alone. The one judgement call is a quote mark right before it: a valid character of a local part, read as a quote because an erased address left behind in quotes is the worse mistake. A mail that staff sent to the person's address on behalf of another attendee (the resend override) loses that address in the erasure itself.
- The Reports tabs and their CSV exports, the delivery log and the Custom fields tab do not know about erased attendees yet: their rows show the placeholder name and no address, and the custom-field answers (deleted at erasure) land in "not answered". Their rows are read with plain queries and no last check, so a report or a CSV read while an erasure is still open carries that person's name and address: the one place the check described above does not reach yet.
- A pass that a creating request could not track for an erased attendee (its save failed, or the event's template changed meanwhile) is not recorded: for an erased attendee the failure marker is skipped too. Its provider id is deterministic (`admitto:<event id>:<attendee id>`), so the erasure's follow-up should also look it up at the provider by that id and delete what it finds.
- Outside Admitto: the mail provider's Sent Items and relay logs, proxy logs, database backups (14 days by default). A restore must re-run the erasures.
- A mail already handed to the sender when the erasure runs can still go out once. Its outcome is not written back: an emptied delivery (no recipient) is skipped by every write-back, so it stays cancelled. The last check before a message goes to the mailer (`readDeliveriesBeforeSend`: a retry, the worker, a synchronous send) reads the delivery under the attendee's row lock, so an erasure that is still open is waited for and a message never starts for someone it is erasing. That holds for a message that staff sent to another attendee's address (the resend override) as well: the delivery belongs to an attendee who is not being erased, but erasing the person who holds that address cancels and empties it, so the check also locks that person's row (found by the address in the delivery's event, whatever its case or padding), in the same statement and in id order, which cannot deadlock with an erasure. One case stays open: a resend that staff address to this person's email while the erasure is still running is created after the erasure has cancelled the waiting ones, and once the erasure commits nothing links the address to the person any more, so that mail goes to an address staff typed. Apart from that, the gap between the check and the mailer call is the only one left.
- A pass update or a push message already with the wallet provider when the erasure runs still arrives, and the pass is deleted right after. The last check before one is sent (`attendeeIsLive` and `liveAttendeeIds` in [`lock-check.ts`](../../packages/tickets/src/lock-check.ts): the pass update, and each batch of a message to many passes) reads the attendee under their row lock, so an erasure that is still open is waited for and nothing starts for someone it is erasing.
- An Add to Wallet request has the same last check at the end: `handleWalletRedirect` takes the attendee's row lock in the transaction that records the device, and a visitor whose attendee is erased by then is sent back to the ticket page, whichever way the URL was obtained (a stored active pass, a pass just created, one another request is creating). It fails closed: if the check cannot be made (the lock gave up waiting behind an erasure, and a second try with the lock alone gave up too) the visitor gets the try-again notice, not the pass; a failure of the device write alone does not block the pass. The transaction that saves a new pass, and the check that follows a failed save, wait behind an erasure of the same attendee with a limit of 65 s (`ERASURE_WAIT_TX_TIMEOUT_MS`): Prisma's default 5 s does not cut a statement that waits for the row lock, but it expires the transaction, and its commit then fails and loses the work. The check after a failed save takes the row lock, so it waits for an erasure that is still open and the pass just created at the provider is deleted when the attendee turns out to be erased.
- Other timestamps the person caused stay exact: mail opened and clicked, RSVP update, first wallet confirmation. Only admission and check-in times are cut to the hour.
