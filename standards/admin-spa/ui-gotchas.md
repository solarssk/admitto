# Admin SPA component and bundling gotchas

Read when you add a component, a dropdown, a modal, CSS, a font, or an import from a workspace package in `apps/admin`.

---

**Font formats (`apps/admin`'s own bundled fonts): woff2 only, no woff/truetype fallback** - the
app's JS already requires a browser new enough that woff2 is a given, so older formats are pure
dead weight in the package-shipped CSS (Tabler icons, `@fontsource` text fonts). This does **not**
apply to organisation-uploaded custom branding fonts (`FontFamilyModal.tsx`, `uploadThemeFont`) -
those accept whatever format the customer's own font file comes in
(`woff2`/`woff`/`ttf`/`otf`, see `FONT_FILE_RE`), and we don't control that. See
[packages/ui/README.md](../../packages/ui/README.md) "Fonts" for the full reasoning, what's currently
shipped vs. stripped, script/locale coverage gaps (Arabic, CJK, RTL), and why the same fix doesn't
mechanically extend to `@fontsource` text fonts (CSS `@import` bypasses Vite's plugin hooks - don't
re-attempt that approach without reading why it failed first).

**`apps/admin` pages are lazily code-split (`React.lazy`) - a component's CSS import must live in
that component's own file, not just "somewhere already loaded on this page".** A modal/component
that reuses another feature's CSS classes (e.g. the shared `add-attendee-modal.css` "standard
modal" markup, or `IconPicker`'s `icon-picker.css`) needs its own `import "*.css"` line even if
some other already-visited lazy chunk happens to load that stylesheet too - that only works by
accident of navigation order within one browser session, and renders fully unstyled on a cold
visit straight to the page that's missing the import. Found via `CreateTemplateDialog.tsx` (in the
lazy `communication` chunk) using `.add-attendee-modal__*` classes with no import of that CSS file
at all. `grep -rn 'import "delivery-modals.css"' apps/admin/src/communication/` - every consumer of
a shared modal/component CSS file should show up importing it directly.

**Do not import `@admitto/mail-templates`, `@admitto/tickets`, or `@admitto/wallet` (package root) from `apps/admin`.** All three barrels re-export Prisma/node-only server modules, and Vite can ship them into a lazy SPA chunk.

| Package | Why it leaks | Safe subpath to use instead |
|---|---|---|
| `@admitto/mail-templates` | Barrel pulls in mjml/fs. Caused `fileURLToPath is not a function` on Event Settings. | `@admitto/mail-templates/placeholders` |
| `@admitto/tickets` | Barrel pulls in Prisma, `node:crypto`, pdfkit, and, via `htmlnano`→`cosmiconfig`'s optional TS-config loader, the entire `typescript` compiler. | `@admitto/tickets/custom-data-reserved`, `@admitto/tickets/event-item-usability` |
| `@admitto/wallet` | Barrel pulls in `node:crypto`, Prisma, and `pg` transitively via `registration-sync.ts`/`passcreator-webhook.ts`; pulled `node:crypto`, `node:url`, `@prisma/client/runtime`, `pg`, and `pgpass` into the Event Settings chunk via the `WALLET_MAPPING_PLACEHOLDERS` import. | `@admitto/wallet/passcreator-mapper`, `@admitto/wallet/capabilities` (static provider facts, type-only imports) |

Same idea as avoiding `@admitto/auth`'s root entry for password helpers (`./constants`, `./password-strength`). Type-only re-exports from the root remain OK when they stay `import type` / `export type`.

**A field in which staff type the details of somebody else (an attendee's email, name, company or phone) takes `attendeeFieldAttrs(key)` from `utils/no-autofill.ts`, not bare `NO_AUTOFILL_PROPS`.** 1Password and LastPass honour the opt-out, but Bitwarden does only for a user who switched that on, and otherwise offers to fill in the staff member's own email, name or phone. The helper adds a `name` that Bitwarden's own test reads as a search box (`test/checkin/bitwardenSearchField.ts`), without the word "email", which Safari's Hide My Email reads.

**A check that the server and a form both make is written once, in `@admitto/shared`, and imported on both sides: never copied into `apps/admin`.** The calendar day of a date answer (`isDateAnswer`, `isDateTimeAnswer`) and a phone number (`isValidContactPhone`) are the examples. A hand copy is counted as duplicated code by SonarCloud, and nothing keeps it in step with the server when the server changes.

A local build's Vite output (`npm run build -w @admitto/admin`) surfaces new leaks as "Module ... has been externalized for browser compatibility" warnings during the `vite build` step: do not ignore them.

**A CSS custom-property fallback (`var(--token, #hex)`) must match the token's real value in `packages/ui/src/styles/tokens/colors.css` exactly.** The fallback only renders when the variable is genuinely undefined (a stylesheet load race, or a standalone page that never imports `colors.css`), so a drifted fallback is invisible in normal use and easy to introduce with a hand-typed hex that's merely close to the real color.

`apps/admin/test/styles/token-fallback-coverage.test.ts` parses `colors.css` at test time (not a hardcoded copy) and fails the build on any mismatch across `apps/admin/src`, `apps/web/src`, and `packages/ui/src`. If you add a new token or a new `var(--x, #hex)` usage, run this test rather than eyeballing the hex.

> **Reusable technique:** when a set of things must each map to exactly one fixed value (an API error code to its UI message, see `apps/admin/test/api/operator-api-error.coverage.test.ts` for `CODE_MESSAGES`; a design token to its fallback; a status enum to its label), write a test that scans real usages and fails on drift, rather than trusting the mapping stays complete by review alone. Neither `tsc` nor a normal Vitest assertion catches this class of gap.

**A `ConfirmDialog` (or any child modal) opened from inside a parent modal must suspend the parent's own `useModalFocusTrap` while it's open:**

```ts
useModalFocusTrap(panelRef, open && !anyConfirmDialogOpen, handleClose)
```

See `apps/admin/src/pages/users/UserEditModal.tsx` and `apps/admin/src/identity/useUnsavedChangesGuard.ts`.

Why: both traps register a capture-phase `keydown` listener on `document`. If the parent's stays active, its listener (registered first, since it mounts before the child dialog opens) fires ahead of the child's on every Escape press, which can reopen a second copy of the same dialog instead of letting the topmost one close.

> **Test this explicitly:** the bug surfaces specifically on Escape (Tab-trapping still works, since focus itself is already inside the child), so a click-only manual test of a nested dialog can look correct while the bug is present. Test Escape whenever a `ConfirmDialog` can appear on top of an already-open modal.

**Moving the focus after an async action waits for the render, in an effect, never in a timer.** A page that is busy turns its controls off, and a browser does not focus a control that is off. A `setTimeout(..., 0)` after the action ran before React had drawn its end in Chrome (jsdom drew first, so the test was green), and the focus fell to `<body>`. Count the finished actions in state and focus in a `useEffect` on that count (`pickerFocusRequests` in `CommunicationPage`); the test records that the target was on when it took the focus.

**Before writing a new dropdown, combobox, or checkbox-list picker, check `apps/admin/src/components/` first.** `SearchableSelect.tsx` (single choice from a list, with a search box past 6 options) and its sibling `MultiSelect.tsx` (same trigger/panel/`useDropdownMenu` mechanism, checkbox rows that stay open instead of closing on click) already cover "pick one" and "pick several" from a fixed option list, including the multi-select filters on the Attendees list (ticket type, attendance, mail delivery status). Reach for `SearchableSelect`/`MultiSelect` even for a page-local, one-off filter.

**A phone number is `PhoneCountrySelect` and a `type="tel"` input beside it, joined and split with `composePhoneE164` and `splitPhoneForPicker` (`apps/admin/src/utils/phoneCountries.ts`).** The event contacts, the account page and the user dialogs already do it, and so does the phone answer of the attendee forms (`CustomDataFieldInput`). Do not write a second phone input; `sanitizeContactPhoneInput` and `isValidContactPhone` (`@admitto/shared`) are the one rule for what a number may contain.

**A floating panel (menu, picker, suggestion list) is placed by `useFloatingPlacement` (`apps/admin/src/components/useFloatingPlacement.ts`), never by your own `getBoundingClientRect()` math.** It uses Floating UI (offset, flip, shift, size against the visual viewport) and applies the result as a `transform` on a `position: fixed` panel at `left: 0; top: 0`, so the panel is never measured squeezed against an edge. `useDropdownMenu` is built on it; a component that keeps its own open state and click-outside (a date, time or timezone picker, an autocomplete list) calls it directly and spreads `panelStyle` on the panel. Hand-rolled copies of this had to be fixed again and again for narrow viewports, a CSS `min-width` wider than the viewport, a max-height that changes the width, and a panel remeasured while visible. A new panel that also sets its own `top`, `left` or `transform` fights the hook. `apps/admin/test/styles/placement-standard.test.ts` fails on an inline `position: "fixed"`, on `attachFixedOverlayLifecycle` or `getFixedOverlayViewport` outside the hook, and on a function that both measures an element with `getBoundingClientRect()` and reads the window's size (`window.innerWidth`, `innerHeight`, `visualViewport`, `documentElement.clientWidth`/`clientHeight`); it reads the code as a syntax tree, so comments, strings and unrelated uses in one file do not count; it is a ratchet, and its only exception today is the `Tooltip` in `packages/ui`, which cannot import the hook.

This class of duplication has already happened silently once: `FiltersMenu.tsx` exists only because the Attendees list's `FilterToolbar` and the Reports admission log had each already written their own copy of the same trigger/panel/badge wiring before anyone noticed and extracted it (see that file's own doc comment).

**A settings row with a label, a description and one `Switch` uses `settings-row settings-row--switch` (`staff.css`), so the switch sits at the vertical middle of the text block, never next to its first line.** A bare `.settings-row` is `flex-start` on purpose (rows with buttons or fields rely on it), so a switch row without the modifier hangs from the top and looks uneven beside Wallet, Security and Branding, which already centre. Do not add a per-panel `align-items: center` class. **A switch in such a row, or in a card header, has no On or Off text:** the title says what it is and the switch shows the state, and the switches then line up on one vertical line ("Off" is wider than "On", so the text pushed them out of line). Give it an `aria-label` that says what it switches. A `label` on a `Switch` is its name, for a switch that stands in a form with no row ("Dry run"), never its state. `apps/admin/test/styles/switch-standard.test.ts` fails for a state text and for a switch with no name.

**An archived event says so once, in the bar `AdminShell` puts above every event page (`ArchivedEventNotice`), and nowhere else.** Panels and screens show it by their locked controls (switches and fields `disabled`, Save and Reset not rendered) and add no "This event is archived" line of their own: staff know it, and a note per panel only pushes the first row down. The Status card on the General tab and the toast after a refused save stay; a tooltip on a disabled button is fine.

**Buttons in a header follow the place, not the screen.** A card header's actions are `Button variant="secondary"` (Fields, Legal), and the slot makes them small (`.at-card__actions .at-btn` in `packages/ui`): never write `size="sm"` there, and a header that needs the large button passes `size="lg"` on purpose. The look (primary, secondary, ghost) is still the call site's. `apps/admin/test/styles/card-actions-standard.test.ts` fails for a `size="sm"` on a button in the actions of a `Card`. A page header's actions are the default size, and a page that must keep them beside the title on a phone compacts them under 768px in its own CSS (`.attendees-pageheader`, `.checkin-pageheader`), never with `size="sm"` in the markup.

**Space around a notice (Registration first):** 12px under the tabs and inside a card, 16px between cards, the same on both sides of the notice. The Requests tab, whose notice and card sit under the tabs, uses 12px for both.

**A hidden input that is `position: absolute` needs a positioned label.** `.at-switch` and `.at-check` are `position: relative`: without it the input sits against the page, far below the fold of a long page, and focusing it (a click on the label does) scrolls the whole shell and shows an empty strip at the bottom of the window.

**A list the person needs only on demand is a collapsible card: `<Card collapsible title="Done" meta={<Badge>7</Badge>}>` (`@admitto/ui`), closed by default.** Use it for a long secondary list (the steps that are done on the Registration Checklist), never for what must be seen or fixed. Anatomy: the whole header row is one `<button>` (Enter and Space work, `aria-expanded`, `aria-controls`), the title is the plain card title, the count or status `Badge` goes in `meta` at the right of the header just before the chevron (the same pill, size and place as the `Badge` that other headers put in `actions`: one rule for every header of a screen), the chevron is the last thing at the right end and turns when it opens, closed is the header alone with no line under it, and its body can neither be seen nor reached (`inert`, then `visibility: hidden` when the closing has finished; the body is mounted from the first render and stays, so opening never mounts it inside the transition), open is header, line and body like any card. It opens and closes smoothly (a grid row from `0fr` to `1fr` with a fade, `--dur-slow`, `--ease-in-out`; nothing but the kit's CSS) and instantly under `prefers-reduced-motion`. The focus ring is the inset ring of the kit (`--focus-ring`), so the card's edge does not clip it. The state is not kept: a visit starts closed. Do not write "Show" or "Hide", do not add a link-style toggle or a `<details>` of your own for a card, and do not pass `actions` (a button inside a button). A placeholder draws it as a header alone (`collapsed: true` on a `SettingsSkeletonCard`). `<details className="disclosure">` stays for a section inside a card (Advanced tuning, Opening hours).

**A card that lists items as rows (Event items, the Fields tab, the Legal tab) uses the one shared table: `item-table` on its section, `<div class="attendees-table-wrap"><table class="table">` inside, and the `requirements-item-*` cell classes.** The table is boxed and inset by the card: the card is a padded `Card` (never `padded={false}`, no negative margins), and the table sits in its own box (1px border, rounded corners, grey header row, hairlines between rows). Its rules are in `components/item-table.css` (the box, fixed layout, one row height, the first column) and not in a page's own CSS; a page sets only the widths of its own columns, with a selector that names its table (`.item-table.legal-table`) so that the order of the stylesheets does not decide. One ladder, by screen width, because the shell has a fixed sidebar from 768px and a 768px screen has about 460px of content: a column that only a wide screen has takes `item-table__wide-only` and repeats its content in `item-table__narrow-only` under the name (under 1024px it has no width and no content, never `display: none`, and the badge moves under the name); under 1024px a switch column is 5rem, the actions column 3rem and the Edit button goes into the row menu, which has an item for it; under 821px the description column of Event items and Fields goes; under 481px the line under the name goes. The name is never squeezed below about 8rem. A table of data in a card (the Import page's columns, rows that are not imported, preview and history) is the same box (`item-table import-table--<name>`): the card is padded, each table sets only the widths of its own columns, a wide one (the preview, the history) scrolls sideways inside its box with a `min-width` that is one class longer than `.item-table .attendees-table-wrap .table` and is the sum of the columns that have a width plus a readable width for each one that has none (14rem for a file name, 8rem for a column of data, counted by the page into a custom property when the columns vary), because a smaller minimum squeezes that column to nothing and scrolling does not bring it back, and a list that can be very long (invalid and skipped rows) has a `max-height` and scrolls inside the box. This is a media query, not a container query, because a container holds the fixed panel of a row's kebab menu inside its own box. A row's menu is the vertical kebab (`ti-dots-vertical`, `useDropdownMenu`, `MoreActionsMenuItem`); an item that the rules block is disabled with its reason as the tooltip and as the line under its name, since a phone has no hover.

**A table that is too wide for its box folds first, then gives way to its cards, and scrolls only when the data sets its width.** The box of a table is the screen less the sidebar (256px), the page padding and the padding of the card: 371px in all, so 653px at 1024px, and a fixed layout cuts every cell that does not fit instead of wrapping it. The columns that stay therefore leave the name (the first column, which takes what is left) at least 9rem at the narrowest screen of each step of the ladder: the style test of the Users page derives it from the stylesheet. (1) Fold what only a wide screen needs: as marks after the name when there are three or more of them (icons with an `aria-label` and a tooltip, so the row stays one line), or as a line under the name or the role when there is one (`item-table__narrow-only`). (2) If the narrowest form still does not fit, the cards that the admin already has take over, from 1024px and not 768px, as in Attendees and Requests: `useIsDesktop(1024)` where code chooses, a `max-width: 1023px` media query where CSS does. (3) Scroll sideways inside the box only when the width comes from the data (the preview of the file in Import), and show that there is more; a log or a list of records is read and acted on row by row, which a card does better. Under 768px every list is cards, as it was.
