# Loading recipes: lists, logs, reports and record pages

Read when you touch a card list, the delivery log, a modal that reads one record, a Reports tab, the Attendees list, the events picker or the attendee page. The shared rules are in [loading.md](loading.md).

---

### Lists and grids inside a card

- A list or a grid inside a card whose title and actions are already there loads through `useCardLoad(list)` (`apps/admin/src/hooks/useCardLoad.ts`, on `useListLoad`: the placeholder gate with its 8 second note, and `useRetryKeepingError`; a list that is enabled and has no answer and no error yet is waiting too, its request starts in the next effect; one that is not enabled, because its tab is closed, is `idle`: no timer runs for it and it draws its placeholder held, never an empty list, so the 200ms and 8 seconds are counted from the request that opening the tab starts, also when the tab was left before the first answer): `RowsSkeleton` (or, for the image library, which loads through `usePanelLoad` because its list is also changed locally, its own grid of placeholders, `AssetGridSkeleton`) for the first load, `RetryEmptyState` for a failure (its Retry hands the focus to the `.at-card` that holds the list, which stays, so the next Tab goes on from there and not from the top of the tab: `useRetryFocusHandover(retryRef, landmark)`), and `RefetchRegion` (rows blocked and dimmed, never replaced) for a later page; a pager (`PaginationFooter`) stays mounted and passes `busy={list.refreshing}`, and the page number it shows is the one asked for, so the rows on screen are those of the page before until the answer is in. The wallet push history (`useWalletPushHistory`) is such a list, enabled only while the Wallet tab is open and read again each time it is. A panel with an imperative handle that refreshes its data after another card has changed it (`EventBounceIngestPanel.refresh`) draws its placeholder for the first read only and keeps its form for a refresh, with the `useRetry` Retry and `PanelLoadError`; its newest read owns the panel (a read that starts aborts the one before it, a save that has returned drops the reads that started before it, and leaving the panel aborts the read), so an older snapshot or an older failure never replaces a newer one or a form that is on screen. A button that adds the result of an earlier step (Add image after the file was picked and uploaded for cropping) has a busy flag of its own, and goes off with `aria-disabled`, not `disabled`, once it has done its job (the form is empty again) so it keeps the focus.

### Live list in a card (Communication delivery log)

- A live list in a card (the Communication delivery log, read as soon as the page is there so the number on its tab is current, and refreshed every 1.75 seconds while **Live** is on) is a card list like the others (`useDeliveryLog` on `useListLoad`, `useCardLoad` in the tab, `DeliveryLogSkeleton` with the real column headings, in the table's or the cards' layout, and rows as tall as the real ones, a `RetryEmptyState`, a `RefetchRegion`, a `PaginationFooter` with `busy`) and its refresh is `list.poll()` from an interval: it shows no sign of itself (no dimming, no `refreshing`), starts nothing while a request somebody waits for is on its way (it never takes over from a page, a search or a Retry), nor while the previous tick is (the answer of a server that is slower than the interval is applied when it comes, and the log is not asked again meanwhile), has no 30 second limit of its own (a server that is slow but does answer is waited for: the limit is for what an operator waits for), is abandoned when **Live** is switched off (`poll(until)`, with one `AbortController` for each stretch of Live: the tick that is on its way has its request cancelled and its answer dropped, so a log that says Paused is never changed by it) and when a read somebody waits for starts (a Retry goes ahead of a tick that has not answered, so one that hangs never holds the next ones back), and by an action that has just changed what the list reads (`poll(undefined, { supersede: true })`, which the Registration requests call after a decision: the tick on its way started before the change and would bring back what it changed, so its request is cancelled and its answer dropped, and a fresh one starts), ignores its own failure (it does not even tell the connection state: `onError` is for the reads that are waited for, and the fetcher is told that a request is a tick, `ListFetcher`'s `{ poll: true }`, so that a 401 on a missed tick does not hand the browser to the login page: the next read somebody waits for does), and its answer replaces the one on screen, also the error of a read that failed, so a log that could not be read comes back by itself. The empty states, the number on the tab and the pager follow the answer on screen; the pager sits outside the ladder of placeholder, error and rows, so a page that fails to load replaces the rows with the error and leaves the pager that was pressed on screen with its focus, Previous being a way back (it is `busy` while a page is on its way, `list.refreshing || list.loading`); an answer whose page is gone (the log got shorter, or the page came back with no rows although the total says it exists, which steps back one page) is waited out like a first load while the page steps back (`useCardLoad(list, { alsoWaiting })`), so it never says "No matches"; the number on the tab leaves with a list that has given way to an error, and stays away until the answer that follows is in (also through the Retry of that error, which keeps the error on screen while the answer left behind is the previous query's: `list.loading`); and the search box asks the server, and goes back to the first page, only when its text differs from what the rows were asked with, so a debounce tick that changes nothing, and a character typed and deleted again, never move the operator off the page they are on. **Clear filters** goes off with `aria-disabled` (it turns itself off on the press that clears the filters), and **Export log** is `Button loading`.

### Modal that shows a record it reads when it opens

- A modal that only shows a record it reads when it opens (`DeliveryDetailsModal`, `SentMessagePreviewModal`) keeps its header, with the title and the recipient (and, in the details modal, the actions of its footer that do not need the record), from the first frame, reads the record once through `usePanelLoad` (the same 200ms, 8 second note and 30 second limit) and shows what `panelView(panel)` says: the placeholder (`DeliveryModalSkeleton`: the real section titles over grey pairs and lines as tall as the real ones, measured in Chrome and named for assistive tech by its status region, held invisibly for the first 200ms), a `Notice` alert whose `action` is a busy **Retry** (with `actionBusy`, so a repeat failure is announced again), or the record. The modal is keyed by the record it was opened for (`<Body key={…}>` inside the exported component), so another record is a fresh modal and its load never follows a changing prop, and the focus recovery of `useModalFocusTrap` moves the focus to the dialog's first control when a Retry that worked removes the button that held it.

### Reports: Event day

- A page whose first tab is a report with a live feed (Reports > Event day) is keyed by the event (`ReportsPage` renders `ReportsPageBody key={eventId}`), and the first read of the tab is `usePanelLoad` (the 30 second limit and a Retry): `failReportLoad` tells the connection state, hands the browser to the login page on a 401 (no error flashes up first) and remembers a 403, so that the error says the viewer has no access. The tab is a `<section aria-label>` that stays whatever the read is doing (`RetryEmptyState` takes its selector as `landmark`, so the focus of a Retry that worked goes there) with one of the placeholder (`ReportsEventDaySkeleton`: the tiles, the chart, the breakdowns and the log with their real titles and headings, measured in Chrome against the real report, 1329px against 1329px), the error, or the report, which, like its empty state, sits in a wrapper (`reports-eventday__ready`, a column with the section's own rhythm) that fades in over 150ms (`at-fade-in`). The silent refresh that a live check-in schedules stays a fetch of its own, which applies its answer with the optimistic count it captured when it started, so a read (and its Retry) cancels it first (`cancelReconcile`): a refresh that landed after a read had reset the count would drive it negative. The Export menu's trigger is the control that holds the keyboard focus once the menu has closed on a click, so a CSV export shows on it (`Button loading`, the menu stays shut meanwhile, as on Attendees) and the rows of the menu are plain: a row of a menu that closes on click is gone while it works.

### Reports: Wallets, Custom fields and Mail tabs

- The other tabs of Reports (Wallets, Custom fields, Mail) are lazily loaded and each reads its own aggregate endpoint once, when the tab is first opened, and keeps its answer while it stays mounted underneath the others (`apps/admin/src/reports/ReportsTabs.tsx`). The code of a report (Recharts is in it) travels with its data, in one read: `Promise.all([fetch, import(report)])` through `useReportFetch` (on `usePanelLoad`, so the wait has one placeholder, one 8 second note, one 30 second limit and one Retry, and a chunk that cannot be loaded is a failed read, not the application's error screen). Do not put a `Suspense` fallback of its own in front of a tab that then loads its data: the fallback and the tab's own placeholder would each hold their 200ms, so a grey shape that had been shown would blink out and come back. The tab is a `<section aria-label>` that stays (`ReportTab`: the placeholder, a `RetryEmptyState` with the section as its `landmark`, or the report in a wrapper, `reports-tab__report`, a column with the section's own rhythm that fades in over 150ms with `at-fade-in`), the placeholder is `ReportTabSkeleton` driven by a spec of the tab's rows in `tabSkeletons.tsx` (each card's real title, how many lines its description takes and what it holds: a donut, a list, a chart, a comparison or a funnel; the rows measured in Chrome against the real tab, to the pixel at 1100px, and a card whose title depends on the data, a custom field's name, shows a bar), and a failure goes through the same `failReportLoad` as Event day's (the connection state hears of it, a 401 hands the browser to the login page, a 403 says that the viewer has no access).

### Attendees list

- The Attendees list (`AttendeesPage` and `AttendeesTable`) is the one list that does not run on `useListLoad` (its request depends on the page, the filters, the sort and the selection), so it follows the time rules by hand. Every request goes through `loadWithTimeout` (30 seconds, and then the error below, never a skeleton or a dimmed list for ever; the `timedOut` flag of `reportLoadListError` tells that from the page leaving). The first read's skeleton has one status region, shared by the table and the cards (`AttendeesSkeletonStatus`): a visually hidden "Loading attendees" and, after 8 seconds (`useDelayedLoading` with `SLOW_NOTICE_MS`), `SLOW_NOTICE_TEXT` in view, in the same region, so it is announced too. A failed list is a `RetryEmptyState` on `useRetryKeepingError(loadError, loadList)`, in a persistent `<section class="attendees-list-section" aria-label="Attendee list">` that also holds the table (the landmark that takes the focus when the Retry works): the table must not take the error's place at the click, because in "refresh" mode with no rows it says "No attendees yet" or "No matches" for a list that has not answered. A refetch over the rows (filter, search, page) has the 30 second limit too, but its bar does not say it is slow yet.

### Screens before an event is chosen (events picker, check-in entry)

- The screens that open before an event is chosen (the events picker `EventsPickerPage` for administrators, `CheckInEntryPage` for door operators) and the start of the session (`AuthProvider`) read once and follow the page rules without `useListLoad`. The request has the 30 second limit (`loadWithTimeout` in the picker; the check-in entry keeps its own timer and abort, which a test holds to leave no timer behind), the loader is `SectionLoader` ("Loading events", "Loading check-in events") behind `useLoadingGate`, held invisibly for the first 200ms, kept for at least 400ms once drawn and with `SLOW_NOTICE_TEXT` as its `caption` after 8 seconds, and what replaces it, the list or the error, fades in (`at-fade-in`, on a wrapper that stays through a Retry so that it plays once; the failed start fades in too). A failed read is a `RetryEmptyState` on `useRetryKeepingError(error, load)`: only an answer clears the error, never the click, and a Retry is not a first load, so the loader must not take the error's place (`loading && !failure.running`). The picker and the check-in entry put the loader, the error and the list in one persistent `<section aria-label>` (`events-picker-body`, `checkin-entry-body`), which is where the focus goes when the Retry works; the session start has no region to hand it to and passes none.

### Attendee page

- The attendee page (`AttendeeDetailPage`) reads its record once and follows the page rules without `useListLoad`. `loadDetail` goes through `loadWithTimeout` (30 seconds; `loadAttendeeDetailData` gives its signal to both requests, `rejectOnAbort` ends the wait for a read that ignores it, and a read that is abandoned because the page was left says nothing and does not end the wait of the one that follows: StrictMode runs the page's effects twice in development). The first read's placeholder is `AttendeeDetailSkeleton` (`attendees/AttendeeDetailSkeleton.tsx`), in the shape of the page and on its own classes, so the stylesheet lays it out at every width as it lays out the page: the header (its Back is real, so a slow read can be left; Edit and More actions are bars), the status chips (four, and Wallet as a fifth only when the event offers a wallet platform, which the event the page already has says: `hasWalletStatusChip`, the question the page's own strip asks too, so the strip has the rows it will have at every width) and the three tabs by their real names, the one the address asks for marked as the open one (`?tab=activity`, `?tab=notes`; any other value is Overview, as the page reads it: `AttendeeDetailPage` passes the tab it parsed, so a deep link never shows the placeholder of a tab that is not the one that opens), over the body of that tab: the Overview cards by their real titles over bars, the rows of the Activity log (a dot, two lines, the time and the actor, each line of text a bar in a line of the height of the text, `Line`) with the pager under them, or the Notes hint in its real words, the composer as bars and one note. Bars drawn straight on the page are as light as its background, so the cards are what make them show (the two lines and one rectangle that stood here before were all but invisible), and the header, the chips, the Profile and Event items cards, the Activity rows and pager and the Notes composer were measured against the real page in Chrome (the rows to within two pixels at 1280px and at 390px). A bar has a width of its own, so the columns of the page's rows that hold bars may shrink (`min-width: 0`) and a bar yields to the room there is on a phone instead of sticking out of the card. It has one status region (a visually hidden "Loading attendee" and, after 8 seconds, `SLOW_NOTICE_TEXT` in view, in the same region; the region takes back the page's row gap until the note is in it). A failed first read is a `RetryEmptyState` on `useRetryKeepingError(error, loadDetail)` in the page's own element, a `<section aria-label="Attendee">` that the error, the not-found notice and the loaded page share (the same key, so the element stays), which is where the focus goes when the Retry works. A Retry is not a first load (`loading && !detail && !failure.running`), so the skeleton must not take the error's place. An erased attendee's page, which the same read can end in, keeps the three tabs (`ErasedAttendeeView` takes the strip from the page, and its Activity log and Notes tabs say that the history and the notes were erased), so the placeholder is never followed by a page that has dropped them.

### Lists that are searched, filtered or paged (useListLoad)

- A list that is searched, filtered or paged, or refreshed after an action, loads through `useListLoad` (`apps/admin/src/hooks/useListLoad.ts`, used by the three Users & roles tabs): only the first load, or the load after a failed one, leaves the placeholder in its place; a changed query or a refresh keeps the rows (`refreshing`, in a `RefetchRegion`); a refresh of the same query that fails keeps them and says so (`refreshError`, a `RefreshWarning` whose Retry is busy from its own click), and what an action has just saved or deleted is applied to them first (`update`, with the pure changes in `apps/admin/src/pages/users/list-changes.ts`, before the `reload`; only what the action knows exactly, checked against the query the list was asked with, so a person who no longer fits the filter leaves it), so a refresh that fails does not make a saved change look lost; when the action changed rows in a way the page cannot tell (a bulk revoke that reports a count, not which sessions; an invite, whose place in the list is the server's), `reload({ keepRowsOnFailure: false })` replaces them with the error instead, and a list that has given way to an error no longer shows its number on the tab label; a changed query that fails replaces them with the error, because they no longer answer what was asked (also when a `reload` took over from a changed query that was still on its way: the rows on screen belong to the previous query); each request has the 30 second limit and an answer that is no longer the latest is dropped. The empty states describe the answer on screen (carry `filtersActive` in the fetched value), never the search still on its way, and they sit inside the `RefetchRegion` too, so a refetch that starts from an empty state is blocked, dimmed and announced like one that starts from rows. An answer with no rows although there are some, because the page it was on is gone (`pastTheEnd`), is waited out like a first load while the list steps back to the page that exists, so it never says "No …". A failed load or refresh is shown by `ListFailure`: a failed load is a `RetryEmptyState` (the placeholder of every failed load: the glyph over a title, the message and a Retry that stays on screen, busy, until the answer is in and hands the focus to the card when it works; `ListFailure` is given the title), so the three tabs and the Archiving list go through `useCardLoad(list)` (with `{ alsoWaiting }` for a page that is gone), the placeholder is not drawn while a Retry runs, and the tab's number leaves with the error and stays away until the answer is in (`failure.error`, not `list.error`, which a Retry clears).
