# Loading recipes: settings panels, editors and whole pages

Read when you touch a settings panel, a modal editor, Event settings, Communication, Overview, Requirements, the Account page or the event deep link. The shared rules are in [loading.md](loading.md).

---

### Settings panel

- A settings panel fills its form from a first load that goes through `usePanelLoad` (`apps/admin/src/hooks/usePanelLoad.ts`, on `useListLoad`, so it has the same 30 second limit, "Taking longer than usual" after 8 seconds and Retry): nothing for the first 200ms, then a `SettingsPanelSkeleton` with the panel's own cards (their real titles, and a label and a control per field, sized by measuring the panel in Chrome: `intro`, `fields`, `columns`, `controlHeight`, `rows`, `rowHeight`), then the form, fading in; a failed load is a `PanelLoadError` (a card with a `Notice` alert: what failed and why, and a Retry that is busy, with the error kept on screen, until the answer is in), and is not also a toast. When a retry works, that card and the Retry that holds the keyboard focus go away, so `PanelLoadError` moves the focus to the `role="tabpanel"` the panel sits in (given `tabindex="-1"` when it has none, and only once the form is mounted; focus that is anywhere else by then, or that was never on the Retry, is left alone), because a browser would drop it on `<body>`: a screen reader then says the tab panel's name and the next Tab goes into the form, so a settings panel must be rendered inside a tab panel. `fetch` takes the `signal` and returns the data, and `apply` puts it into the panel's own state with only the newest answer; neither needs to be stable, and a request that ignores its signal still stops being waited for after 30 seconds (`rejectOnAbort`). `retry` is for a failed first load only: a panel that is loaded is never reloaded under its form. The Save button of `SettingsFooter` is `Button loading` (its label does not change, and "Uploading…" is gone: a logo upload shows its own state in its drop zone), and Save and Reset go off with `aria-disabled`, never `disabled`, because the button that has just done its job turns off on the same commit and would lose the keyboard focus; a list inside a panel (Archiving) goes through `useListLoad` like the Users lists, and an action applies its result first (`update`). An intro that wraps is drawn as `intro: <lines>`; a panel whose shape depends on its data (the Mail panel, which has no Sender or transport settings cards until a transport is chosen) draws the commonest shape, with a bar for a title that is not known yet; and a card that is shown for one event (`EventMailSettingsCard`) is a fresh card for another (`key={eventId}`), so its load never needs to follow a changing prop. A panel's own actions (Test connection, Send test, each recipient's test) are `Button loading` or `IconButton loading` with their own flag, like any other, and a button that has an `aria-label` of its own gives a busy one too ("Sending test (webhook)"). A file on its way (a logo in `LogoUploadZone`, a font in a `FontFamilyModal` row) is shown where the file is chosen, not as a changed label: a `Spinner` in place of the icon (an empty drop zone is just its spinner, since its invitation to drop a file would be wrong; one that shows a logo keeps it and only gets the bar) and, for a zone, a `TopProgressBar placement="container"` along its top edge (indeterminate: `fetch` reports no upload progress), with the status said once for assistive tech (a visually hidden status outside the zone, because the zone is a `role="button"` whose children a screen reader flattens; the zone is named "Uploading logo", `aria-busy` and `aria-disabled` meanwhile, and its Replace image and Edit image buttons use `aria-disabled`, never `disabled`; for a font row, the spinner's own label), and the button of a dialog that runs the work (Apply in `CropImageModal`) is `Button loading`.
### Modal editor that fills its form from a record

- A modal editor that fills its form from a record it reads when it opens (`CfAccessEditor`, and `IdentityProviderEditor` in edit mode) keeps the modal's own header, with its real title and subtitle, from the first frame, and draws the form's own cards as the placeholder (`IdentityEditorSkeleton` in `apps/admin/src/identity/`: the cards with their real titles, a label, a control and a hint per field, sized by measuring the real form in Chrome, held invisible for 200ms, "Taking longer than usual" after 8 seconds): the Cloudflare Access editor loads through `usePanelLoad`, the provider editor through `useProviderLoad` (the same 30 second limit, a 404 is `not_found`, each run owns its `AbortController`, and its state belongs to the provider id it was reached for, so a changed id is the placeholder from the very render that has it and covers the form of the previous provider). A failed load is `IdentityEditorLoadError` with a busy Retry, and the modal's focus handling (`useModalFocusTrap`, re-run when the view changes) keeps the focus in the dialog when it works (on its first control, the Close button, not in the form). A 401 on a load hands the browser to the login page (`redirectToLogin` in `identity/loginRedirect.ts`; `orLoginRedirect` wraps a load that goes through `useListLoad` or `usePanelLoad`, and never answers, so no error flashes first; the scope lookups of the mapping repeater, read after the editor's record, pass `redirectOnUnauthorized` to `useEventOptions` and `useOrganizationOptions` for the same reason). A screen that is not an in-page tab (the Identity routes) still wraps its content in a labelled `role="tabpanel"`, so that `useRetryFocusHandover` has a panel to hand the focus of a Retry that worked to; and an optimistic change that the server may not have taken (a provider's enabled switch) reconciles with `reload({ keepRowsOnFailure: false })`, so a refresh that fails too shows the error and not the unconfirmed value.
### Event settings: tabs that each read their own data

- A page whose tabs each read their own data (Event settings) keeps its header and tabs on screen from the first frame (`EventSettingsHeader`) and reads the record the whole page needs once, through `usePanelLoad` in a body that is keyed by the route's id (`EventSettingsPage` renders `EventSettingsPageBody key={eventId}`, so another event is a fresh page and its first load never has to follow a changing prop); until it has answered, the open tab draws a `SettingsPanelSkeleton` of its own cards (`EventSettingsSkeleton`: the Location, Check-in and Mailing tabs reuse the cards their own panel draws, so the two placeholders look the same; the others are hand-sized cards, and General, Location, Ticket types, Check-in and Danger zone were calibrated against the real tab in Chrome), and a failed read is a `PanelLoadError` inside a labelled `role="tabpanel"` (never a toast and a blank page). When the Retry works the page replaces the error entirely, so a focus that has fallen to the page when the error goes (nothing holds it: it was on the Retry) is handed to the page's open tab panel by the page itself (`useFocusAfterPageRetry`, below, which leaves focus that is anywhere else alone), not by `PanelLoadError`, whose own panel is gone with the error. A reload of the same record after an action (archive, restore, the bulk Danger Zone actions) is `load()`: the page is on screen then, so a failure of it is a toast and the page stays (a 403 or 404 still turns it into "Event not found", as it always did). A tab's own panel (`CheckInBehaviourPanel`, `LocationSettingsPanel`) loads through `usePanelLoad` the same way, in a body keyed by `eventId`, and a list inside a card whose title and actions are already there (`TicketTypesCard`, the Identity providers) shows `RowsSkeleton` (rows of the height of the real ones) and a `RetryEmptyState`, never an empty list before the answer.

### Pages whose first read gates every tab (Event settings, Communication)

- A page whose whole first read gates every tab (Event settings, Communication) shares its error and hand-over code: `PageRetryPanel` (`components/PageRetryPanel.tsx`) is the labelled tab panel that holds the error and notes, when it goes, whether the focus was inside it, and `useFocusAfterPageRetry(failed, settled, rootRef, errorHadFocusRef, targets)` (`hooks/useFocusAfterPageRetry.ts`) hands the focus to the first existing target (the open tab's panel, the selected tab button, the Back button) only when it was, because the page replaces the error and `PanelLoadError`'s own panel is gone with it. The header and the tabs are one component used by the placeholder, the error and the page (`EventSettingsHeader`, `CommunicationHeader`), so they never remount. A page keyed by its route's id (`CommunicationPage` renders `CommunicationPageBody key={eventId}`) must also make what was still on its way for the previous id stale when the id changes: the sequence numbers that those guards compare (`saveSeqRef`, `metadataSaveSeqRef` and the other seq refs) are bumped in the cleanup of the body, otherwise a save that finishes after the switch still toasts, because the old instance never sees the new id. The cleanup does so only when the route is on another id (`CommunicationPage` keeps the current one in a ref that a layout effect sets, which runs before the old body's cleanup; a navigation straight to another event's other page, which unmounts the page without re-rendering it, is told by the address bar that the router has already moved, `addressBarIsOnAnotherEvent`): an operator who has just left the page for another page of the same event, or for a page that belongs to no event, still hears how a save or a delete ended. A lazily loaded editor's `Suspense` fallback is the editor's own card as grey shapes (`TemplateEditorFallback`, which gates itself with `useLoadingGate`), not a spinner.
### Dashboard: the event Overview

- A dashboard that reads one answer for the whole page and refreshes itself (the event Overview) keeps the frame that comes from the event (the header, the archived notice and its restore dialog) on screen whatever the body is doing, and the body, in a `<section aria-label>` that stays (`PanelLoadError` takes its selector as `landmark`, so the focus of a Retry that worked goes there), is one of three things: the placeholder (`OverviewSkeleton`: the KPI tiles with their real labels and a grey bar for each count, the countdown real because it comes from the event, the cards with their real titles; measured in Chrome against the real page, 939px against 938.5px), the error (one `PanelLoadError`, never dashes, "No activity yet" or an add prompt, which would pass for an event with nothing in it), or the page, which has its answer, so no card needs a loading or an unavailable branch (`assertPresent`), in a wrapper (`overview-stack__page`, a column with the stack's own rhythm) that fades in over 150ms (`at-fade-in`). The first read is `useListLoad` with `useCardLoad` (the 30 second limit and a Retry); the refresh every 30 seconds and the one after a live signal are `poll()`: silent, with no time limit, and a refresh that fails changes nothing on screen, while one that works after a failed first read replaces the error by itself. The fetcher reports every failed request to the connection state, ticks included, because a session that ended must still send the browser to the login page. The page is keyed by the event (`EventOverviewPage` renders `EventOverviewPageBody key={event.id}`), and the effect that records which event it shows clears it on cleanup, so a restore or a save that finishes after the route moved touches neither the layout nor the page. The Save and Add of the Pinned note, contact and link dialogs are `Button loading` with the label they have at rest ("Saving…" is longer than both), and Cancel is `disabled` while they work.
### Page of cards gated by one read (Requirements)

- A page of cards that the first read of the whole page gates (Requirements: the event's items and its custom fields, read together, since the edit drawer needs both) is a wrapper that renders a body keyed by the route's id (`RequirementsPage` renders `RequirementsPageBody key={eventId}`, so another event is a fresh page, with no state to reset in an effect), and its read is `useListLoad` with `useCardLoad` (the 30 second limit, "Taking longer than usual" after 8 seconds, a busy Retry that keeps the error on screen): the header stays, and a `<section aria-label>` that stays whatever the read is doing (`RetryEmptyState` takes its selector as `landmark`, so the focus of a Retry that worked goes there) holds the placeholder (`RequirementsSkeleton`: the cards with their real titles and column headings over rows in the real cells, so that the stylesheet's own row height applies, measured in Chrome against the real page, 630px against 630px at 1100px, and no button to add anything to before the read has answered), the error (a 403 says that the viewer has no access, with a Retry, since access can be granted meanwhile; a 401 goes to the login page through `orLoginRedirect` once the connection state has heard of it) or the cards in a `RefetchRegion`, inside an element that fades in over 150ms (`at-fade-in`). What an action saves exactly is applied at once (`list.update` for the Active switch), and what it adds, changes or deletes somewhere the page cannot tell is read again with `reload({ keepRowsOnFailure: false })`: the cards stay, blocked and dimmed, while it runs, and a refresh that fails replaces them with the error, since they may be wrong. A dialog's button that starts the work (Create in Add item, Save in the item drawer) is `Button loading` with the label it has at rest ("Creating…" and "Saving…" are longer), goes off for a reason of the form with `disabled` (a `disabled` passed with `loading` is ignored while it is busy), and the field that Enter submits is `readOnly` meanwhile, with the submit handler ignoring a second submit while it works (Enter does not go through the button, which swallows a click).

### Account page

- The Account page (`AccountPage`) reads its account, its sessions and its notification preferences once, each with the 30 second limit, and a failed read keeps its error and a busy Retry on screen (`useRetryKeepingError`; the gate does not count a running Retry as a wait, and the cards follow `failure.error`, not `error`, which a Retry clears while the older answer is still held, so a stale list or an empty grid is never shown meanwhile). The errors of the sessions and the notifications are a `RetryEmptyState` inside their card, which stays, so the focus goes to the card when the Retry works. The error of the account itself gates every tab, so it is a `RetryEmptyState` in a `PageRetryPanel` and the focus goes to the open tab's panel (`useFocusAfterPageRetry`), inside the one element (`pageRef`) that holds the placeholder, the error and the page.
### Event deep link (EventLayout)

- The event of a deep link (`EventLayout` in `App.tsx`, when the navigation did not hand the event over) is read once and follows the page rules without `useListLoad`. The read goes through `loadWithTimeout` (30 seconds; `rejectOnAbort` ends the wait for a read that ignores the signal; leaving the page, or moving to another event, aborts it and says nothing, and so does the first run of StrictMode's double effect), the loader is `PageLoader` ("Loading event", from the first frame, with `SLOW_NOTICE_TEXT` as its `caption` after 8 seconds, counted again for another event: the restart key of `useDelayedLoading`), and the status of a failure decides what it means: a 401 hands the browser to the login page (`redirectToLogin`, no error flashes first), a 403 or 404 goes to the picker (the event is not there for this viewer), and anything else, the 30 seconds included, is a `RetryEmptyState` on `useRetryKeepingError(loadError, loadEvent)` in a `shell-loading at-fade-in` box that stays through a Retry, with a **Back to events** button below it (there is no shell yet, so no menu to go back with). No focus is handed over when the Retry works: the whole shell replaces the error, as it does at the start of the session.
