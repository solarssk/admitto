### Added

- **Attendees list — bulk change attendance status.** The bulk bar's "More actions" menu gains a **Change attendance status…** entry that opens a picker of the fixed attendance states (Confirmed, Tentative, Declined, Cancelled, Registered) and sets the chosen one for every selected attendee at once — same shape as bulk change ticket type, including the three-way result toast (updated / already-set / none-found, the last one meaning the selection no longer resolves to real attendees) and an `rsvp_status_changed` activity-log entry per attendee actually changed, marked `source: "admin"` like the existing single-attendee edit path. Disabled on archived events. Bot review: the picker dialog and the result-toast logic were each independent copy-pastes of bulk change ticket type's own — now a shared `CardPickerDialog` and `notifyBulkAssignResult` back both features, so a future fix to either only needs to land once. The bulk write also now reuses `computeRsvpChange` (the single-attendee PATCH path's own write-payload logic) instead of hand-duplicating it, and the picker's fixed status list is derived from `RSVP_LABELS`' own keys instead of a separately hand-typed array, so it can't silently drift from the `RsvpStatus` union. `BulkRsvpResponse` is now a type alias of `BulkTicketTypeResponse` rather than a byte-for-byte duplicate. Follow-up code review: the "More actions" menu itself had the same duplication one level up — its eight items (Send tickets, Export selected, Change ticket type, Change attendance status, Revoke check-in, Revoke items, Revoke pass, Delete) were each a hand-written Tooltip+button+icon+label/hint block; they're now one shared `MoreActionsMenuItem` component, with no change to any item's tooltip text, disabled logic, or accessibility semantics. The server-side transaction shape was the last remaining duplication: `handleBulkRsvpEventAttendees` and `handleBulkTicketTypeEventAttendees` now share `applyBulkAttendeeChanges` (diff owned rows against a target, write only what changed, log one entry per changed row, report updated/already-set counts) — each still does its own findMany and any pre-transaction validation/locking (the ticket-type catalog lock), but the identical tail end is no longer duplicated. Second bot review: both endpoints read every selected attendee's current value, then wrote every changed row in one blanket `id IN (...)` update — a concurrent single-attendee PATCH landing on one of those rows between the read and the write was silently overwritten back to the bulk's target, and the activity-log entry it wrote recorded a "from" value the row no longer actually held. `applyBulkAttendeeChanges` now writes via a single per-row-conditional `UPDATE ... FROM (VALUES ...)` statement keyed on each row's own value read moments earlier, so a row a concurrent edit changed in that window is left untouched (not clobbered, not logged with a stale "from") and reported back as a new `conflictCount` alongside `updatedCount`/`alreadySetCount`. Code review on #569: `CardPickerDialog`'s Apply button now carries the same 10s "don't act on reflex" arm-before-confirming cooldown (depleting progress bar included) as the bulk Delete/Revoke dialogs — a misclick on a large batch could otherwise overwrite everyone's ticket type or RSVP status in one shot with no confirmation at all. Both pickers gained it together to stay consistent with each other. Follow-up: the new `conflictCount` from the CAS fix above reached the response but not the operator — `notifyBulkAssignResult` only ever read `updatedCount`/`alreadySetCount`, so a raced attendee vanished from the toast with no indication anything was skipped, and a selection where every attendee raced showed the "may have been removed" error (wrong — they were found, just raced). The toast now notes "(N skipped — changed by someone else just now)" alongside the existing already-had-it note, with its own message for the all-raced case. Bot review on the CAS fix: `applyBulkAttendeeChanges` picked `=` vs `IS NOT DISTINCT FROM` per caller via a `nullable` flag documenting each column's DB nullability — a future caller passing the wrong value for its own column would silently miscount every currently-unset row as a conflict. `IS NOT DISTINCT FROM` is null-safe and behaves identically to `=` for a non-nullable column, so the flag added a footgun without adding a capability; removed in favor of always using it. PO catch: the cooldown's "Please wait Ns before confirming" message rendered via a plain native `title` attribute on both `CardPickerDialog` and `ConfirmDialog`'s own Apply/confirm buttons — a leftover from before this app's shared `Tooltip` component existed — showing the browser's default tooltip instead of the app's own; both now wrap the button in `Tooltip` like every other disabled-reason hint in the app. SonarCloud: `MoreActionsMenuItem`'s class-name string nested one template literal inside another (`` `more-actions-menu__item${variant ? ` more-actions-menu__item--${variant}` : ""}` ``, flagged S4624) — rewritten as an array `filter(Boolean).join(" ")`, the same pattern `Tooltip` itself already uses to combine class names.

Works on archived events too (it's read-only), goes through the same sanitized export pipeline as the existing formats (formula-injection guards, no tokens, audit-log entry recording how many rows were requested and exported), and ids from outside the event are ignored server-side.

Reuses the exact same single-use CAS admission path scan check-in already goes through (ADR 0010 §4) once per selected attendee, so every existing guarantee — no double check-in, per-attendee activity log entry, badge issuance if the event has one configured — applies unchanged; there's no bespoke bulk logic to drift out of sync with the real thing. Fires immediately with no confirmation dialog (it's a reversible internal state change, not an email send) and reports back with a toast breakdown (e.g. "4 attendees checked in (1 already admitted)"). Blocked on archived events, matching Send tickets and the single-attendee revoke-checkin action — checking someone into an event that's already over doesn't make sense.

- **Attendee detail — Delete attendee, a GDPR erasure entry point in the admin SPA (closes #356).** The `DELETE` API has existed since v0.4.6, but fulfilling an erasure request meant using internal tooling or a manual DB script — the admin UI had no delete button. A new **Delete attendee** item in the Attendee Detail page's **More actions** menu (styled red, below a divider) opens a confirmation dialog requiring the operator to type the attendee's exact name before the button unlocks, same "drunk click" safeguard already used for permanently deleting an event. Confirming permanently removes the attendee's profile, ticket deliveries, wallet pass, and check-ins in one transaction and writes an audit log entry, then redirects to the attendees list with a success toast. Unlike every other action in the same menu, Delete attendee is not blocked on archived events — an erasure request can legally arrive after an event ends, and the backend endpoint never blocked on `archived_at` either, so the UI now matches. [DSAR-PROCEDURE.md](docs/DSAR-PROCEDURE.md) updated to point at this new UI path instead of "use your internal tooling." Polish pass (PO review): the confirmation dialog's message no longer references DSAR-PROCEDURE.md by filename — operators clicking the button aren't going to go read a doc — and now lists what gets removed as a proper bullet list instead of one run-on sentence. Deleting an attendee (single or bulk) now also writes an entry to the central admin **Audit log** (Instance Settings, superadmin-only), alongside the existing per-attendee record — previously an attendee's own activity trail disappeared along with the row it was about, leaving no record anywhere of *who* erased them; attendee creation gets the same central record for symmetry. The Attendees list's row-selection bulk bar gained a matching **Delete** action inside a new **More actions** menu (an extra click to even reach it, matching the design mockup and the same danger-item treatment already used on the attendee detail page), erasing every selected attendee at once with the same removal scope, a 10-second arm delay before the confirm button unlocks (matching the Danger Zone's other bulk actions), and the same "not blocked on archived events" behavior as the single-attendee action. Second polish pass (PO review): the central admin audit log entries for attendee create/erase now include the event's title and the attendee's own name/email, not just opaque ids — unlike the per-attendee log (which stays deliberately PII-free, since re-logging the very data just erased would defeat the point), this one-off exception is scoped to the superadmin-only central log and grounded in GDPR Art. 33/34's breach-notification duty to identify affected individuals (documented in [DATA-PROTECTION.md](DATA-PROTECTION.md)).

A simple toggle (Organization mail / Dedicated for this event) switches between the two; picking "Dedicated" starts from a blank form rather than a copy of the organization's settings, and reverting back to "Organization mail" removes the event's override entirely rather than leaving stale, unused credentials behind. The transport picker, sender fields, and secret handling (set/change/clear, never round-tripped in plaintext) reuse the same components already shipped for the organization-wide Instance Settings → Mail page, so the two screens behave identically. "Send test email" on the event's Mailing tab verifies whichever transport actually resolves for that event — its own dedicated one, or the inherited organization one — and is available to any admin who can manage the event, not just superadmins (unlike the organization-wide Mail settings, which stay superadmin-only). Deferred to a later change: managing templates for system/administrative email separately from this transport-level setting.
- **Reports — ticket type badges and breakdown now read the per-event catalog (closes #387).** The admission log's "Ticket type" column shows the same colored badge used everywhere else in the app (Attendees, check-in) instead of plain text, and the "By ticket type" breakdown chart gets a matching color dot per row and colors its bar to match. A configured type with zero admissions still shows up in the breakdown (e.g. a "Press" type nobody has checked in under yet) instead of only appearing once someone actually has it, and the admission log's type filter lists configured types instead of whatever raw strings happen to be in the data. CSV and PDF exports show the catalog's display label the same way. Depends on the "Ticket types" catalog above — a fresh install or an event with no configured types just shows an empty breakdown, same as having no attendees.
- **Event Settings — Ticket types: per-event catalog replaces free-text guest types (closes #351).** Admins now define an event's ticket types (label + color) once on a new "Ticket types" tab in Event Settings, instead of typing a guest type by hand every time — which used to let "VIP", "vip", and "Vip" drift into three different-looking entries, with only "vip" ever getting a colored badge. Each type gets a color from a curated 8-color palette (a small swatch picker), shows a live badge preview and how many attendees currently have it, and can be renamed or recolored anytime; deleting a type is blocked while any attendee still has it. Every place that used to accept a free-text ticket type now reads from this catalog instead: the add/edit attendee form is a dropdown, the attendees list "Type" filter and the Communication bulk-send "by ticket type" filter both list only configured types, and CSV/XLSX import matches a row's `ticket_type` value against the catalog (case-insensitively, by name or key) — an unmatched value is skipped at commit with a clear reason in the import preview, instead of being written to the database as-is. New events get one default "Standard" type automatically; existing events are migrated on upgrade — each event's past ticket-type values are grouped case-insensitively into one canonical entry apiece (preserving today's purple "vip" coloring, everything else neutral), with every attendee's stored value normalized to match, so nothing needs fixing by hand after the update.
- **Requirements — Custom attendee fields registry (closes #372).** Event-wide attendee data fields (dietary requirements, parking, or anything else that isn't tied to a specific hand-out item) now have their own management card on the Requirements page — define a field's label, type (text/select/boolean), required flag, and options once, independent of any event item. Event items reference these fields to show one as an operator hint at check-in (e.g. a gift bag's shirt size) instead of each item separately redeclaring the same field with its own metadata, which is what let two items disagree about the same field before. The check-in operator card, the attendee edit/create form, CSV/XLSX import, and export columns all read a field's definition from this one registry now, so a field defined once is consistent everywhere it's used. A field can only be deleted from the Requirements card, and is blocked (409) while any item still shows it as a hint. Existing events are migrated automatically on upgrade — any field previously declared only inside an item's config is copied into the registry as part of the deploy's migration step, before the server starts serving traffic, with no operator action needed.
- **Event Settings — Danger zone: "Revoke all check-ins" and "Revoke all items issued" (superadmin only):** two new bulk actions to undo things that happened on an event without visiting each attendee one at a time. **Revoke all check-ins** clears the checked-in status for every currently admitted attendee at once (they can check in again afterwards); **Revoke all items issued** resets every issued/returned item hand-out (e.g. badges) back to "pending" for every attendee, independently of check-in status. Both reuse the same per-attendee logic already used by the individual "Revoke check-in" / "Revoke item" actions, are blocked on archived events (same as the rest of the Danger zone's mutating actions), disable themselves when there's nothing to revoke, and confirm with a plain Yes/No dialog stating the live count — no typed confirmation, since the action is fully reversible. Each destructive Danger zone confirm button now also holds a **10-second countdown** before it becomes clickable (a thin depleting progress bar under the button label, same button size) — enough time to reconsider before a bulk/irreversible action fires. A third **"Revoke all Wallet passes"** row is a disabled placeholder for now — Apple/Google Wallet passes aren't built yet.
- **Event Settings → Branding: image asset library for custom email tokens.** Superadmins can upload named branding images (e.g. a sponsor logo) scoped to an event and reference them anywhere in that event's email templates as `{{name}}` — resolved to the uploaded file's URL at send/preview time exactly like the built-in `{{logo_url}}`/`{{header_image_url}}`. Names must start with a letter and contain only lowercase letters, numbers, and underscores; a name that collides with a built-in placeholder or an existing asset is rejected with a clear message. A 2 MB per-file limit and a per-event asset count limit apply. ### Security
- **Bumped `svgo` (via `@tabler/icons-webfont`'s `svgtofont` build tool) from 3.3.3 to 3.3.4**, fixing a high-severity advisory (GHSA-2p49-hgcm-8545: the `removeScripts` plugin left some executable scripts intact) `npm audit` flagged. Scoped to just that nested dependency via `overrides`, so the other `svgo@4.x` used by `mjml`/`postcss-svgo` is untouched. `svgtofont` only runs at build time to generate the icon webfont — this was never reachable at runtime — but the fix is free and keeps `npm audit --audit-level=high` (a required CI gate) green.
- **Event-level dedicated mail transport (#511) could be used to redirect the organization's real SMTP password or Power Automate key to a server the event admin controls.** Because the event and organization mail configs resolve field-by-field (an event can override just one field and inherit the rest), an event admin — a role with less access than the superadmin-only organization Mail settings page — could save an event override that set only the connection target (SMTP host, or Power Automate URL) while leaving the credential unset, causing the organization's real password/key to be sent to that attacker-chosen endpoint on the next send or on the event's own "Send test email" (which every event manager already has access to). Saving or sending now requires an event that overrides its own connection target to also supply its own credential — it can no longer silently borrow the organization's. Microsoft Graph is unaffected: a mismatched tenant/client always authenticates against Microsoft's own servers, never an event-admin-chosen one, so there is nothing to redirect.
- Fixed a related gap in the same mail-settings validation: submitting a request that only clears a secret (e.g. wiping the stored SMTP password with no other change) skipped completeness validation entirely, silently leaving an active transport unable to authenticate with no error shown — now validated like any other change. Also closed a race where two concurrent saves to the same event's mail settings could each validate against stale, pre-write state and together leave a configuration that was never actually validated as a whole.
- Admin SPA: audit `ApiError.message` exposure — toasts and inline errors now go through `operatorApiErrorMessage()` so unknown server detail is suppressed with a generic fallback (dev console warning only).
- Identity JSON API (`/api/admin/identity/providers*`, `/api/admin/identity/cf-access*`): catch blocks no longer forward raw `err.message` to the client. Unexpected/Prisma errors now return `{ error: "save_failed" }` (HTTP 500) with full details logged server-side only; domain validation errors return `{ error: "validation_failed" }` (HTTP 400); discovery failures return `discovery_failed`; invalid issuer URL returns `invalid_issuer`; invalid/missing CF Access team domain returns `invalid_team_domain` / `team_domain_required`. Integration tests cover all error code paths including simulated DB failures via `vi.mock("@admitto/auth")` factory.
- **Delete event (#395) is layered against both an accidental click and a compromised superadmin session, without requiring an event to be archived first.** The button is disabled unless the event shows zero real activity across 7 independent signals (0 attendees, no items beyond "Badge", no contacts, no resources, no pinned note, no event-specific mail template, no event-scoped action-log entries) — a genuinely-used event can never be deleted regardless of its archived status, so a separate "must archive first" step would only add friction, not safety. The server independently re-validates the exact same guard on every `DELETE` request; it never trusts the settings DTO's `is_deletable` hint, which exists only to drive the button's disabled state. Deleting also requires typing the event's exact title to confirm — an empty confirmation value can never satisfy this and fails closed. `DELETE /api/admin/events/:eventId` is superadmin-gated and CSRF-protected like every other mutating admin route; a concurrent activity change between the guard check and the delete is caught by the database's own foreign-key safety net and reported the same as any other "not deletable" rejection.
- **Dev server no longer binds to every network interface by default.** `npm run dev -w @admitto/web` was reachable from any device on the local network at the dev machine's LAN IP, not just `localhost` — an unintended exposure surface for a tool that handles attendee PII. It now binds to loopback only unless a local mkcert HTTPS cert is present (the existing opt-in phone-over-LAN camera-testing workflow, which still needs to be LAN-reachable). Production is unaffected — it still binds to all interfaces, as required to accept traffic from the container network / reverse proxy.
- Self-service account actions (password change, MFA enroll/reset, session revoke) are now recorded in the admin audit trail — previously only the admin-on-another-user equivalents were logged, so a user changing their own credentials left no trace (#472).
- **Fixed a self-lockout: enrolling MFA from Account settings while already logged in silently broke the current session.** Confirming TOTP enrollment marks backup codes as unacknowledged (IAM-002), which every subsequent request re-checks — but only the login-time enrollment flow ever cleared that flag. A self-service enroll (already-`full` session) never reached that step, so the very next request after confirming was rejected with no explanation, and the account-level acknowledgment endpoint itself required a partial (non-`full`) session the user no longer had — the only way out was logging out and back in. Self-service confirm already shows backup codes at the enroll step, so the fix marks them acknowledged immediately on confirm instead of requiring a separate step.
- **Resetting your own 2FA now requires a current authenticator (or backup) code, not just your password, for accounts whose role requires MFA.** Previously `POST /api/account/mfa/reset` deleted every MFA method after checking only the password — weaker re-auth than linking an extra SSO identity already required. This closes a path where a password-only compromise (without also breaking the second factor) could be used to permanently strip and replace an admin/superadmin account's MFA. Mirrors the existing password+TOTP step-up already used for SSO account linking; accounts whose role doesn't require MFA are unaffected.
- **MFA verify rate-limit buckets are now namespaced per action.** `checkMfaVerifyRateLimit` — shared by SSO account linking, TOTP enrollment confirm, and the MFA-reset step-up above — keyed its per-session/IP buckets only by session/IP and code shape, with no action tag. Fumbling one self-service action (e.g. confirming a new TOTP enrollment) could 429 an unrelated one in the same session (e.g. resetting a lost MFA method), and vice versa — not an auth bypass (sharing the bucket only made rate-limiting stricter, never weaker), but confusing. Each of the three self-service call sites now passes a distinct action tag (`oidc-link`, `mfa-confirm`, `mfa-reset`); the login-time MFA step-up flow is unaffected.
- **Changing your own password now requires a current authenticator (or backup) code, not just your current password, for accounts whose role requires MFA.** Previously `PATCH /api/account/password` only re-verified the current password — someone who had hijacked a live full-session cookie and separately learned the account's password (without also breaking its MFA) could use it to change the password and lock the legitimate owner out, without ever needing to defeat the second factor. Mirrors the step-up already required for self-service MFA reset above; accounts whose role doesn't require MFA are unaffected.
- `POST /api/admin/sessions/:id/revoke` (superadmin revoking another user's session) wrote an audit row even when the session was already revoked — a retry, double-click, or two concurrent revokes of the same session left duplicate `session_revoked` entries with no real effect behind them. The revoke and its audit write now happen in one transaction, gated on the session actually being revoked by that call.
- **Event-level mail transport settings (#511) now require superadmin, matching the organization-wide Mail settings page, instead of any organization admin.** A pentest found that an ordinary event admin — someone managing one event, not the whole instance — could point an event's Power Automate webhook URL or SMTP host at an address on Admitto's own internal network and, via the existing "Send test email" feature, make the server issue a real outbound request there, with part of the response echoed back to them. Mail transport is technical configuration (credentials, webhook URLs, SMTP hosts), not everyday event management, so the "Mailing" tab is now hidden from non-superadmin event settings the same way the "Integrations" tab already is.
- **Mail transport destinations (Power Automate URL, SMTP host) are now checked against a private/loopback/link-local/cloud-metadata address blocklist, both when saved and immediately before the server connects.** Independently of the authorization fix above, this closes the underlying server-side request forgery outright — reuses the same address-validation logic already proven for OIDC provider discovery, so a misconfiguration or a future config surface can't turn either transport into a way to reach internal infrastructure.
- Attendees list/detail/export endpoints (participant names, emails, ticket data — including the CSV/PDF/XLSX export) now send `Cache-Control: no-store`, matching the pattern already used on Reports and Event Settings exports, so a shared cache or browser can't retain this personal data longer than intended.
- Every `/api/*` JSON response now carries the baseline security headers (`nosniff`, `X-Frame-Options`, `Referrer-Policy`, HSTS) at the application layer — previously only the `/healthz` and `/readyz` ops probes set them explicitly, leaving every other API response to depend entirely on the reverse proxy adding them.
- The post-login redirect allowlist now also rejects a raw tab character, a known technique for bypassing URL-blocklist checks — not currently exploitable (a separate role-prefix check already blocks this shape), but closed as defense-in-depth.
- **Closed a DNS-rebinding gap in the mail transport blocklist above: the address check and the real connection could be tricked into resolving a hostname differently.** The blocklist validated a mail destination's DNS records, but then let Power Automate's `fetch` and SMTP's `nodemailer` connect by re-resolving the same hostname themselves — a malicious or compromised DNS server could answer safely for the validation lookup and answer with an internal address moments later for the real connection, bypassing the check entirely. Both transports now pin the real connection to the already-validated address instead of re-resolving: Power Automate reuses the DNS-pinning pattern already proven for OIDC provider discovery (an `undici` dispatcher pinned to the validated address, keeping the real hostname for TLS SNI); SMTP resolves and validates the host before building its connection pool at all, then connects to the validated address directly.
- **`POST /api/admin/users` (create account, superadmin only) ran the full Argon2id password hash before checking whether the email already existed.** A duplicate-email request cost exactly the same CPU as a real account creation — there was no cheap way to reject a flood of duplicates, letting a compromised or malicious superadmin account slow down other users' logins (which also hash via Argon2id) with minimal effort of their own. The handler now looks the email up first and returns `409 email_taken` immediately on a match, before Argon2id ever runs; the existing unique-constraint catch stays as a safety net for the rare create/create race.
- **Attendee search/list (`GET /api/admin/events/:eventId/attendees?q=...`) had no rate limit, unlike the neighboring export/import endpoints.** The `q=` search runs an unindexed `ILIKE` across 6 columns (2 of them JSONB), so any single logged-in account — including a plain operator, not just admin/superadmin — could saturate the database's CPU for every tenant just by firing enough concurrent requests, no special tooling required. Added an `admin:attendees-search` rate-limit policy (120 requests/minute per user per event, matching the existing per-user-per-event pattern used by `admin:import-preview`), wired onto the same route as every other admin data endpoint.
- **CI's Postgres test service no longer has a hardcoded password.** `ci.yml` previously set `POSTGRES_PASSWORD: admitto` in five places, tripping SonarCloud's hardcoded-secret rule (`secrets:S6698`) — the value was never a real credential (the database exists only for one CI run, on a runner no other job can reach), so a repo secret was tried first, but Codex review on the PR caught that a secret resolves to empty on a fork-originated `pull_request` run (GitHub withholds secrets from those), which would break Postgres startup for any future fork contribution. Switched instead to `POSTGRES_HOST_AUTH_METHOD: trust` for these ephemeral, network-isolated service containers — no password needed at all, so there's neither a literal to flag nor a secret to fail to resolve.
- **The production Docker image no longer defaults to root (`docker:S6471`).** The image had no `USER` directive, so a plain `docker run`/`docker exec` against it got root by default — the running web server itself already dropped to the `node` user via the entrypoint's own `su`, but only after starting as root to write pre-migration backups into the root-only `migration_backups` volume (a deliberate hardening: if the app process is ever compromised, it still can't read or tamper with its own DB dumps). Split that root-only work out into a new one-shot `migrate` compose service (`user: root`, runs migration status check, pre-migration backup, `prisma migrate deploy`, and backfills, then exits); the `app` service now sets `USER node` in the `Dockerfile` and only starts once `migrate` completes successfully, execing the HTTP server directly with no migration logic and no filesystem access to `/backups` at all (not even mounted). Disaster-recovery backup restore commands in `deploy/README.md` now target the `migrate` service instead of `app`, matching where `/backups` actually lives. Best-effort retention cleanup (expired auth sessions/trusted devices, stale mail-delivery snapshots) moved to run in `app` itself rather than `migrate` — `migrate`'s completion is only checked on `docker compose up`, so a bare `app` restart (crash loop, `docker compose restart app`, `restart: unless-stopped`) would otherwise silently stop running it on every boot the way it always had (bot review). Follow-up review pass: `migrate` no longer inherits the image's port-3000 `HEALTHCHECK` (it never listens on anything, so that probe could only ever misreport it "unhealthy" mid-run on a slow backup/migration); the migration-backup smoke test's restart scenario now actually asserts the retention log line reappears, not just that the container comes back up; two stale doc references to the old single-service entrypoint (`deploy/README.md`'s backup section, `docker-compose.yml`'s `migrate` comment) are corrected.
