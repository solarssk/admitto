# @admitto/db

Database layer for Admitto. PostgreSQL is the single engine across dev, CI and production (ADR 0004).

## Prerequisites

- [Docker](https://docs.docker.com/get-docker/) to run PostgreSQL locally (or a native PostgreSQL 16 you create the databases in yourself; `npm run db:test-setup` falls back to local `psql`/`createdb`)

## First run

```bash
# 1. Start Postgres
docker compose -f infra/docker-compose.yml up -d db   # from repo root

# 2. Configure connection
cp packages/db/.env.example packages/db/.env          # already set for docker-compose defaults

# 3. Migrate (the Prisma client is generated by `npm install` via postinstall, or on demand with `npm run db:generate -w @admitto/db`)
npm run db:migrate -w @admitto/db
npm run db:seed -w @admitto/db      # idempotent - safe to run multiple times
npm run db:test-setup               # from repo root - creates admitto_*_test DBs for package tests
```

Or from the repo root using the delegating scripts:

```bash
npm run db:migrate
npm run db:migrate:status   # check applied migrations / schema drift
npm run db:seed
```

## Scripts

| Script | Description |
|---|---|
| `db:generate` | Generates the Prisma client from `prisma/schema.prisma` |
| `db:migrate` | Applies pending migrations (`prisma migrate deploy`), then runs the idempotent backfills in order: agency `public_ref`, event custom-field registry, ticket-type catalog, check-in session id, event actor attribution, email-delivery template label / had-wallet-CTA / template id snapshots, and JIT password hash. The production `migrate` service runs the same sequence |
| `db:migrate:dev` | Creates a new migration from schema changes during development (`prisma migrate dev`) |
| `db:migrate:status` | Shows which migrations are applied and whether the schema has local drift |
| `db:backfill-public-ref` | Idempotent TS backfill for agency rows missing `public_ref` (also runs at end of `db:migrate`) |
| `db:backfill-event-custom-fields` | Idempotent backfill of the per-event custom-field registry (also runs during `db:migrate`) |
| `db:backfill-ticket-types` | Idempotent backfill of the per-event ticket-type catalog (also runs during `db:migrate`) |
| `db:rebind-secret-contexts` | Manual, never part of `db:migrate`: rewrites legacy encrypted secret columns (mail credentials, event wallet API key, IMAP bounce password, notification webhook URL) as purpose-bound values. `-- --dry-run` previews; exits 1 if a value cannot be decrypted. Rewritten values cannot be read by an older release |
| `db:seed` | Inserts the default organization, 1 event (with a location) and 4 attendees (upsert by `(event_id, email)` - mirrors real import logic). Refuses to run when `NODE_ENV=production` |

From repo root, `npm run db:test-setup` creates the `admitto_*_test` databases the package tests use
(`admitto_tickets_test`, `admitto_db_test`, `admitto_import_test`, `admitto_mailer_config_test`,
`admitto_mail_templates_test`, `admitto_mail_delivery_test`, `admitto_auth_test`, `admitto_web_test`).
It is idempotent and required before `npm test` when using a local Postgres.

## Schema change policy

Additive-by-default (ADR 0027 expand-contract). Production upgrades must never destroy data.

1. **Expand** - add columns/tables (nullable or with defaults) in release N.
2. **Backfill + verify** - dual-write/read; backfill in release N or N+1.
3. **Contract** - drop old columns/tables in a **later** release after nothing reads them.

**Renames:** add new column → backfill → switch application code → drop old column. Do not use raw
`RENAME COLUMN` / `RENAME TABLE` in a release that still runs older code.

**Destructive SQL** (`DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, `DELETE FROM`, `ALTER COLUMN TYPE`, `SET NOT NULL` on
existing columns, `DROP` without `IF EXISTS`) is blocked in CI for **new** migration folders. Override
only with PR label `migration-destructive-approved`, SQL comment
`-- destructive-approved: <reason>`, and Opus pre-merge review.

**Never edit** an existing `prisma/migrations/<name>/migration.sql` after merge - add a new migration
folder instead. The CI guard scans only newly added files (`git diff --diff-filter=A` vs `main`).

**Production path:** only `prisma migrate deploy`, run automatically by the one-shot `migrate` compose
service before the `app` service starts (it fails closed on a failed or unrecognised migration
state). Never `migrate reset`, `db push`, or `db push --force-reset` against production.

## Import

```ts
import { prisma } from '@admitto/db';
import { type AttendeeStatus, type CheckInStatus, CHECKIN_STATUS } from '@admitto/db';
```

Importing the root entry `@admitto/db` constructs the shared `prisma` client immediately (it reads
`DATABASE_URL`). Code that must not open a connection (the admin SPA, test setup) uses the
side-effect-free subpaths instead: `@admitto/db/client` (the `PrismaClient` class, the `Prisma`
namespace and model types), `@admitto/db/status`, `@admitto/db/roles`, `@admitto/db/instance-org`,
`@admitto/db/errors`, `@admitto/db/wallet-pass-fields` and `@admitto/db/adapter`. Test-only:
`@admitto/db/test-db-guard` (refuses any `DATABASE_URL` that is not a `*_test` database) and
`@admitto/db/testing` (`createTestPrismaClient`).

## Statuses

TypeScript unions in `src/status.ts` are the single source of truth for all status values
(no Prisma enums for status values - kept as String for portability and consistency).

| Type | Values |
|---|---|
| `AttendeeStatus` | `registered \| confirmed \| cancelled \| revoked` |
| `EmailDeliveryPurpose` | `initial \| resend` |
| `EmailDeliveryStatus` | `queued \| accepted \| sent \| delivered \| failed \| bounced \| rejected \| cancelled` |
| `WalletPassStatus` | `pending \| active \| voided \| failed \| expired` |
| `CheckInStatus` | `VALID \| ALREADY_CHECKED_IN \| INVALID \| REVOKED \| UNDO \| UNKNOWN_EVENT \| NETWORK_ERROR` |

`CheckInStatus` covers scanner validation outcomes. Only `VALID`, `ALREADY_CHECKED_IN`, `REVOKED` and
`UNDO` (undoing a check-in) are persisted to `CheckIn`; `INVALID`, `UNKNOWN_EVENT` and `NETWORK_ERROR`
are response-only (no resolved attendee, so no row is written).

## Schema notes

- `Attendee.token_hash` - SHA-256 of the raw token; null for agency (Mode B) attendees.
- `Attendee.qr_payload` - agency-provided QR payload preserved as source of truth.
- `Attendee.external_uuid` - agency UUID; unique per event `(event_id, external_uuid)` for idempotent re-import.
- `CheckIn.event_id` - denormalised for event-scoped queries; composite FK `(attendee_id, event_id)` → `Attendee(id, event_id)` prevents cross-event mismatches.
- `CheckIn.status` - one of the persisted values above (`VALID`, `ALREADY_CHECKED_IN`, `REVOKED`, `UNDO`), recorded at scan time.
